# 知乎评论采集

## 正式样本

2026 年 11 月 24 日（北京时间）共核验 20 条，含试采 5 条。知乎专栏荔枝品种讨论 6 条，知乎问答生鲜购买与联系种植者讨论 6 条，知乎日报水果快递讨论 7 条，知乎日报荔枝选购讨论 1 条。每条在两次独立取回的原站评论列表中具有相同的原始编号和逐字相同的正文。表中同时保留两次访问时间、首次顺序、父评论编号和原页显示的发表时间。

普通问答及专栏采用页面默认顺序。知乎日报采用官方公开短评列表返回顺序，每页首批最多 20 条。按 `sources-full.txt` 的来源顺序与首访原页顺序选取，集齐 20 条后停止。入选评论涉及荔枝、樱桃、玉菇瓜或未指明的水果，个别发言人质疑价格或配送承诺。这些均为历史发言者自述，不能作为当前广州运输时效或长健农业产品评价。20 条中没有明确说明购买水果是为了送礼。

- `full.csv` 是正式样本。`review-full.csv` 是本轮由 AI 助手逐条筛选并标注的入选清单。`screening.csv` 记录原始候选的显示顺序、复核状态、排除理由或备用来源状态。
- 知乎日报记录在 `source_url` 提供能直接打开的知乎官方读者留言链接，按 `source_id` 可定位原文。对应的历史文章分享页及用于查找篇名的公开标题索引在原始 JSON 的 `article_url`、`archived_title_index` 内。部分旧文章分享页已无法显示正文，因此保存评论使用当前可读的官方留言列表。标题索引只用作定位，全部留言均直接取自知乎。
- `raw-full` 存原站两轮公开评论字段与其他候选的访问记录。日报读取每条公开原文、编号、时间、父评论编号，不收集用户名和头像。`raw-edge` 是访问失败的备用浏览器记录，未用于提取样本。
- 离线重建正式表的命令为 `py -3.12 -B collect.py --replay --sources sources-full.txt --raw-dir raw-full --review review-full.csv --limit 20 --csv full-replay.csv`。不需要浏览器或网络。
- 联网复查知乎日报可依次运行 `py -3.12 -B collect_daily.py --stage collect --raw-dir daily-new` 和 `py -3.12 -B collect_daily.py --stage verify --raw-dir daily-new`，需要 Python 3 和 requests 包。`collect.py` 的正常网页采集方式见下文。新一轮数据写入新目录，以保留本轮原始证据。

## 试采 5 条

2026 年 11 月 24 日（北京时间），在知乎专栏《中国荔枝排行榜：哪里的荔枝最好吃？》默认评论列表中先后独立读取两次。两次原页记录各含 15 条首屏可见评论（含嵌入的回复），按首访顺序取前 5 条符合要求且复访时相同的评论。原页链接在 CSV 的 source_url 内，配合 source_id 定位单条评论。浏览器首次打开有超时，取两次实际成功访问作为采集和复核，时间以原始文件为准。

优先候选《春节走亲访友什么礼物好？》的轻量移动页可读正文但没有展示评论文本。另查“嗨吃一夏”与“荔枝品种选购指南”，前台显示“添加评论”。普通 Python 请求评论接口返回 HTTP 403 并指示需要登录。最终用 Python 经本机 BrowserOS Neo 的正常访客网页打开替代原页，关闭可关闭的登录提示后，点击“50 条评论”。脚本读取页面已渲染的评论文本、顺序、原站编号、显示日期与父评论编号。

这些是普通荔枝品种及选购讨论，均未提到给别人送礼或购买长健礼盒。说明购买依据、品尝体验或购买疑问才列入；如“本惠州人表示确实如此”“合江晚熟荔枝在国内也算好吃的”等仅表示附和或泛泛评价的回复没有进入试采表。

## 文件与复现

- `raw` 存两次实际浏览得到的原始可见评论字段。采集不保存账号资料或登录信息。
- `review.csv` 记录本轮由 AI 助手依研究问题逐条筛选的评论编号、原文及标注的上下文和主题。组员尚需自行审核；Python 双访核验只检查编号与原文。遇到新原文时先审阅，再从原始数据生成 CSV。`pilot.csv` 支持 Excel 打开。
- 仅重放本批证据：`py -3.12 -B collect.py --replay --csv replay.csv`。输出顺序由原始列表决定。
- 重新联网复查：`py -3.12 -B collect.py --raw-dir raw-new --csv recheck.csv`。需要本机 Node.js、Python 3 和 BrowserOS Neo 的 MCP bridge；其他机器通过 `BROWSEROS_BRIDGE` 指定其文件。两次正常独立读取都找得到同一编号和完全相同的可见原文才算通过。原站排序或评论变化可能导致新批次变少。
